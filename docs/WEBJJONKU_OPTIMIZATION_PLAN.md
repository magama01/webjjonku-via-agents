# 웹쫀쿠 공통 실행 환경 최적화 계획

작성일: 2026-09-18

## 범위와 목표

특정 업무 프로젝트와 무관하게 Codex·Claude·agy에서 사용하는 웹쫀쿠 실행 환경을 최적화함. 대상은 이 저장소의 Oracle 실행기, DevSpace 연결, 브라우저 수명, 세션 매핑, 결과 회수, 스킬 배포임. 이 문서는 계획이며 런타임 변경·설치·브라우저 실행은 수행하지 않음.

목표는 사용자가 매번 명령과 모델 옵션을 설명하지 않아도 동일한 동작으로 실행하고, 창 전환과 중복 제출 없이 결과를 회수하는 것임. 사용자의 호스트 에이전트 세션당 Project 하나를 사용하고 같은 세션의 후속 작업은 해당 Project를 재사용함. 개별 실행 식별자인 run_id와 호스트 대화 식별자인 session_id를 구분함.

## 현재 확인된 상태

이번 점검은 소스·파일 비교·기존 상태 기록에 한정됨. 현재 계정의 실제 모델 목록, 연결 도구, 브라우저 초점 동작 및 설치된 Oracle의 최신 호환성은 실환경 검증 대상으로 남김.

## P0: 모든 에이전트에서 같은 실행 결과 만들기

### 1. 실행 경로와 설정 단일화

- 기존 `chatgpt_oracle_run.py`를 유지하고 모든 스킬이 동일한 배포본을 찾도록 정리함. 신규 실행 프레임워크나 MCP 서버는 만들지 않음.
- 기존 설정 로더를 먼저 확인하고 모델·effort·런타임 경로 설정을 재사용함. 설정 우선순위는 명시 CLI 인자 → 공통 사용자 설정 → 기본값으로 문서화함.
- 실행 요약에 실제 runner 경로, Oracle 버전, 설정 출처를 표시함. 인증정보는 포함하지 않음.
- portable 스킬·연동 안내를 배포 목록에 포함하고, Claude/agy의 실제 스킬 검색 경로를 확인해서 연결함. 임의 환경변수를 제품이 자동 제공한다고 가정하지 않음.
- source, installed, 실제 호출 경로를 별도로 검증함. 설치 반영은 진행 중인 실행을 방해하지 않는 시점에 수행함.

완료 기준: 세 에이전트의 dry-run이 동일한 runtime·모델·effort 해석을 보여주고, 배포 대상 파일의 소스/설치본 해시가 일치함.

### 2. 모델 선택 실패를 제출 전에 명확히 처리

- 사용자 선호를 반영해 기본값을 `gpt-5.6-sol` / `extended`로 정렬하는 것을 제안함. 실제 UI에서 High로 선택됐는지 검증함.
- AGENTS·정책·스킬의 Latest/Pro 강제 설명도 함께 수정함. 명시적으로 요청한 다른 모델·effort는 그대로 존중함.
- 모델 선택·effort 확인은 기존 Oracle 기능을 사용함. UI가 바뀌면 설치 버전과 upstream 지원을 먼저 비교하고 필요한 호환 수정만 적용함.
- 모델 불가, 한도 소진, 로그인 만료, 선택 미확인을 구분함. 임의 모델 변경이나 프롬프트 재제출은 하지 않음.

완료 기준: 정상 모델은 최종 선택 증거와 함께 제출되고, 없는 모델은 제출 전 종료되며 원인과 복구 방법이 결과에 남음.

### 3. session_id와 run_id 역할 정리

- host 종류와 실제 대화 ID로 세션을 식별하고, Project는 `(host, session_id, 정확한 root)`에 매핑함. run_id는 각 미션 실행에 계속 사용함.
- 호스트 ID가 없는 CLI 실행은 명시 session_id를 받거나 단발 실행으로 격리함. 임의로 주변 세션을 인수하지 않음.
- 현재 문자 치환·잘라내기 대신 원본 식별자 묶음의 해시로 매핑 키를 생성함. 기존 항목은 원본 일치가 확인될 때만 호환 처리함.
- Project 이름은 표시용으로 유지함. 동명 Project도 URL/ID로 구분함.
- 공통 owner 정보로 실행·복구를 일관되게 검증함. 기존 Codex 소유권 검증을 제거해서 호환성을 확보하지 않음. 과거 기록은 원래 권한을 유지함.

완료 기준: 같은 호스트 세션의 두 실행은 같은 Project, 다른 세션은 다른 Project를 사용함. 다른 소유자의 reconnect는 거부됨. 긴 ID·특수문자 ID가 충돌하지 않음.

## P1: 브라우저 간섭·복구 비용 줄이기

### 4. 결과 회수와 attention_required 처리

- 기존 상태 체계에서 제출 전 실패, 제출 여부 불명, 생성 중, 응답 저장 완료를 구분해서 표시함. 중복 상태 관리 계층은 추가하지 않음.
- output.md가 없거나 비어 있으면 완료로 처리하지 않음. 저장 후에만 해당 실행 소유 탭을 닫음.
- 명백한 제출 전 실패는 진단 기록을 저장한 뒤 소유 브라우저 정리가 가능하도록 함. 제출 여부가 불명확하면 탭을 보존하고 같은 실행을 관찰함.
- 에이전트가 결과를 놓친 경우 기존 run의 저장 결과부터 조회함. 재실행을 기본 복구로 제안하지 않음.
- 스킬에 상태 확인·동일 실행 재연결·결과 경로 보고를 포함함. transport 완료와 미션 성공은 따로 보고함.

완료 기준: 모델 실패, 응답 대기 중 연결 단절, 결과 회수 후 정리 실패 각각에서 중복 제출이 없으며 다른 탭은 유지됨.

### 4-1. 브라우저 장애 시 무한 대기 방지 — P0로 우선 적용

현재 execute와 reconnect 모두 `process.wait()`에 외부 제한이 없고 Oracle에 `--browser-timeout 100m`를 전달함. Oracle 자체가 멈추면 내부 타임아웃만으로 상위 실행의 종료를 보장할 수 없음. 실제 과거 장애 원인은 별도 로그 조사가 필요하지만 이 대기 경계는 소스에서 확인된 보완 지점임.

- 기존 실행기 안에 유한한 관찰 예산을 둠. 실행 전체 deadline과 복구 횟수를 상태 파일에 저장해 reconnect·프로세스 재시작 때 예산이 초기화되지 않도록 함. 별도 LLM 감시 에이전트는 사용하지 않음.
- 로컬 감시는 프로세스 생존, CDP 연결, 정확한 소유 탭의 renderer 응답, 대화 상태를 구분함. 프로세스가 살아 있다는 사실이나 반복 heartbeat 출력만으로 정상 진행이라고 판단하지 않음.
- 제안 초기값은 30초 간격 점검, 개별 CDP 점검 5초 제한, 연속 3회 연결/renderer 실패 시 복구 진입, 자동 복구 최대 2회임. 모델 생성 한도는 이 장애 감지 한도와 분리하고 현재 100분 예산을 우선 유지하되 상위 감시에도 유한한 여유 시간을 둠. 수치는 실환경 결과로 조정함.
- 답변 텍스트가 한동안 늘지 않는 것은 긴 추론에서도 발생하므로 정지 확정 근거로 사용하지 않음. 로그인 만료·쿼터·명시적 오류 화면은 별도 실패로 즉시 알림.
- 복구는 기존 저장 결과 확인 → 같은 탭에 CDP 재연결 → 탭이 유실됐을 때 저장된 정확한 대화 URL로 재개방 순서로 진행함. URL 재개방은 프롬프트 전송 없이 기존 대화와 해당 사용자 turn/응답을 확인하는 작업임. 현재 binding 검증이 탭·포트를 고정하므로 새 탭 복구에는 기존 소유권과 원래 대화/turn을 입증하는 명시적 재바인딩이 필요함.
- 같은 탭이 생성 중이면 새로고침하지 않음. 대화 URL을 저장하지 못했거나 제출 여부가 불명확하면 목록에서 비슷한 채팅을 추측해 인수하지 않음.
- 제출 확인 시점에 conversation URL·turn 식별 근거를 조기에 저장함. 가능한 경우 응답 일부를 `partial` 산출물로 보존하되 완료 결과로 승격하지 않음.
- 복구 예산을 소진하면 `attention_required`와 구체적 이유를 저장하고 자동 관찰을 종료함. 사용자에게 마지막 확인 단계, 결과/부분 결과 유무, 대화 URL, 재개 방법을 한 번 보고함. 상위 스킬도 같은 상태를 무한 재조회하지 않도록 함.
- 관찰 종료는 서버 측 생성·파일 작업 취소와 다름. 소유권이 확인된 관찰 프로세스만 제한적으로 정리하고 브라우저·프로필·기록은 복구 가능하게 보존함. 새 미션 재제출은 실제 수행 여부 확인 및 사용자 판단 없이 자동 실행하지 않음.

완료 기준: renderer 멈춤, Chrome 종료, CDP 끊김, Oracle 프로세스만 생존, 로그인 만료를 주입한 시험에서 유한 시간 안에 결과 회수 또는 명확한 중단 상태로 수렴함. 재연결 후에도 예산이 유지되고 프롬프트 추가 제출은 0회임. 장시간 정상 추론은 단순 출력 정체로 실패 처리하지 않음.

### 5. 창 전환과 시작 지연 개선

- 기본은 현재 hidden-window 흐름을 유지하고 macOS에서 실행 전후 활성 앱 변화를 측정함. 숨김 옵션 자체를 초점 비간섭의 증거로 간주하지 않음.
- 프로필 복사 시간, Project 초기화 시간, 브라우저 시작 횟수를 기록함.
- 신규 Project 생성 후 동일 브라우저·탭에서 미션 제출까지 이어갈 수 있는지 검토함. 현재 두 단계 시작을 줄이는 변경을 브라우저 풀 도입보다 먼저 평가함.
- headless는 로그인·DevSpace 도구·응답 회수·재연결까지 통과한 경우에만 선택 가능한 실행 방식으로 추가함.
- 공유 브라우저 상시 실행이나 풀은 측정 결과 시작 비용이 유의미할 때만 검토함. 공유 시에도 소유 탭과 프로필 수명 규칙을 유지함.

완료 기준: 일상 앱이 활성 상태인 반복 시험에서 불필요한 초점 이동이 없고, 변경 전후 시작 지연·메모리 사용량을 비교할 수 있음.

### 6. Project 메모리 격리

- 새 Project 생성 UI에서 project-only memory 지원 여부와 선택 상태를 확인함. 사용자가 요청한 격리 범위 안에서 적용함.
- 설정을 확인할 수 없으면 격리 미확인으로 표시하고 전역 개인화 설정 변경으로 대신하지 않음.
- 기존 Project는 설정 변경 가능 여부를 확인함. 불가능하면 기존 작업은 보존하고 이후 새 세션부터 적용함.

완료 기준: 새 Project 생성 시 격리 설정의 관찰 근거가 남음. Project가 분리됐다는 사실만으로 메모리 격리 완료를 선언하지 않음.

## P2: 사용량과 대기 시간 최적화

### 7. 미션 전달과 문맥 관리

- 웹 위임이 설정된 세션에서는 짧은 작업 요청만으로 미션 작성·실행·회수까지 스킬이 담당함. 전역 자동 위임은 별도 기본 정책으로 명시함.
- 미션은 목표, 정확한 root, 읽기/쓰기 범위, 필요한 파일, 산출물, 검증 조건만 포함함. 전체 로컬 대화를 반복 복사하지 않음.
- 같은 Project의 후속 작업에도 필요한 사실·결과 경로를 명시함. Project 메모리가 모든 앞선 내용을 정확히 전달한다고 가정하지 않음.
- 작은 파일 수정 등은 로컬 처리, 긴 분석·독립 검토는 웹 위임하는 기준을 두되 사용자 지정이 우선임.

### 8. 병렬 처리와 측정

- 독립 분석을 요청한 경우 기존 multi 실행기를 재사용함. 기본은 단일 실행이며, 병렬 수는 2개부터 실제 한도·메모리·성공률을 측정해 결정함.
- 같은 파일에 쓰는 미션은 병렬화하지 않음. 한도 소진 때 추가 제출을 멈추고 진행 중인 결과부터 회수함.
- 기존 실행 기록에 시작/Project 준비/제출/완료/저장 시각, 실패 단계, 재연결 횟수를 추가하는 최소 계측을 우선함. 별도 대시보드는 만들지 않음.
- 주요 지표는 제출 성공률, 결과 회수율, 제출까지 지연, 중복 제출 수, 초점 이동 수, 실행 후 잔존 브라우저 수임. 지연은 표본이 쌓인 뒤 중앙값과 p95로 비교함.
- API 과금 절감이나 웹 쿼터 무제한을 가정하지 않음. 실제 사용 제한과 호스트가 소비한 문맥량을 별도로 기록 가능한 범위에서 비교함.

## 토큰 최적화: P0와 함께 우선 적용

### 확인된 비용 구조

현재 일반 실행 경로는 Oracle stdout/stderr를 파일로 보내고 Python의 `process.wait()`로 종료를 기다림. 이 내부 대기 자체는 LLM 호출이 아님. CDP 상태 조회나 로컬 타이머 역시 그 자체로 모델 토큰을 소비하지 않음. 그러나 호스트 에이전트가 반복 도구 호출로 상태를 확인하고 로그를 문맥에 받아 판단하면 호출·결과·후속 추론이 누적됨. 이전처럼 직접 Oracle 실행 로그의 “Waiting…” 출력을 반복 회수하는 운용을 줄일 필요가 있음.

종료 시 현재 실행기는 전체 `state`를 `result`로 반환함. 상세 상태를 매번 모델에 노출하는 대신 저장 파일을 유지하고 짧은 요약을 반환할 여지가 있음. 토큰·쿼터 산정 방식은 호스트별로 다르므로 반복 문맥의 모든 토큰이 매번 동일하게 과금된다고 가정하지 않음.

### 1. 대기는 실행기가 맡고 에이전트 호출은 줄이기

- 기존 실행 프로세스와 호스트의 백그라운드 실행·완료 알림을 우선 사용함. 지원되는 호스트에서는 제출 후 완료 또는 조치 필요 시에만 에이전트를 깨움.
- 완료 알림이 없는 호스트만 상태 폴링을 사용함. 긴 대기를 하나의 차단 도구 호출로 처리하지 않고, 로컬 감시자가 대기하도록 함. 에이전트가 수행하는 조회는 초기 30초 이후 60초 등으로 간격을 늘리고 상한을 두는 방식을 적용함.
- 상태가 바뀌지 않으면 전체 로그를 반환하지 않음. `run_id`, `status`, 변경 여부 정도만 전달함. 내부 heartbeat는 파일에 유지함.
- 오류 때만 해당 단계의 제한된 로그를 읽음. 출력 파일 전체를 반복 읽거나 같은 미션을 재제출하는 폴링은 금지함.
- 기존 도구가 완료 알림을 제공하면 새 상주 서비스나 메시지 브로커를 만들지 않음.

### 2. 전달 문맥을 파일 참조와 변경분으로 줄이기

- 미션에는 목표·제약·관련 파일 경로·완료 조건을 간결하게 기록함. 파일 경로로 이미 접근 가능한 소스나 기존 보고서를 프롬프트에도 중복 삽입하지 않음.
- 후속 요청은 기존 결과 경로와 바뀐 요구사항만 전달함. 웹 도구가 파일을 읽는 비용까지 사라지는 것은 아니지만, 호스트의 재독·재요약 비용을 줄일 수 있음.
- 운영 규칙은 스킬에서 기존 공통 정책을 참조하도록 하고, 긴 정책 전문을 매 요청마다 붙이지 않음. 요청별 쓰기 범위와 제약은 생략하지 않음.
- 일상 요청마다 웹에서 계획만 받고 호스트가 다시 긴 작업 지시를 만드는 왕복을 줄임. 사용자가 승인한 범위 안에서 분석·작업·검증을 하나의 미션으로 묶음.

### 3. 결과는 짧은 요약을 먼저, 상세는 필요한 부분만

- 기존 CLI 사용자를 깨지 않도록 간결 출력 옵션을 추가하고 에이전트 스킬에서 사용함. 전체 상태와 원문은 기존 파일에 보존함.
- 기본 반환 항목은 run_id, 상태, 결과 경로, 짧은 결론, 변경 파일·검증 요약, 필요한 다음 조치임. 내부 브라우저 메타데이터와 전체 실행 인자는 상세 조회로 분리함.
- 웹 미션이 상세 보고서와 짧은 인계 요약을 함께 만들도록 함. 별도 LLM 호출로 요약을 다시 만들지 않음. 요약 목표 길이는 일반 작업 300~600토큰으로 시작하되 사용자 요청·중요한 오류·검증 실패를 잘라내지 않음.
- 호스트는 요약을 먼저 읽고 판단에 필요한 근거·diff·검증 결과만 추가 조회함. 원문 저장, 요약 수신, 실제 작업 성공은 구분함.
- 사용자에게 최종 보고서를 그대로 보여주기 위한 회수와, 호스트가 다음 작업을 결정하기 위한 회수를 구분해 불필요한 재서술을 줄임.

### 측정과 완료 기준

- 호스트 측 도구 호출 수, 무변화 폴링 횟수, 반환 로그 크기, 미션·요약·상세 회수 크기를 실행별로 기록함. 실제 usage를 얻을 수 있으면 입력·출력·캐시 토큰을 분리하고, 없으면 문자/바이트 추정치임을 표시함.
- 호스트 토큰과 웹 측 사용량은 별도로 비교함. 단순히 읽기를 웹으로 옮겼다는 이유로 전체 토큰 절감이라고 보고하지 않음.
- 같은 종류의 짧은 미션과 긴 미션을 변경 전후 비교함. 대조군 없이 절감률을 확정하지 않음.
- 완료 알림 지원 호스트의 목표는 무변화 LLM 폴링 0회임. 일반 성공 경로에서는 짧은 완료 요약을 한 번 회수하고 상세 원문은 필요한 경우에만 읽음.
- 토큰 감소와 함께 실패 감지 지연, 결과 누락, 사용자의 진행 상황 확인 가능성을 확인함. 요약만 믿고 검증을 생략하는 방식으로 절감하지 않음.

## 구현 순서와 검증

1. 기존 변경분 보존 → 공통 설정·배포 경로 정리 → 모델 기본값·문서 정합성 수정함. 간결 반환·파일 인계·호스트 완료 알림 활용을 함께 적용함.
2. session/owner 매핑 및 기존 기록 호환을 검증함.
3. attention_required와 응답 회수·탭 정리 경로를 검증함.
4. hidden-window 초점 시험과 Project 메모리 설정 확인을 수행함.
5. 시간·메모리 계측 후 브라우저 시작 재사용을 적용함. 병렬 확장은 마지막에 수행함.

회귀 검증은 기존 `test_chatgpt_oracle_execute.py`, `test_chatgpt_oracle_run.py`, `test_oracle_startup_hygiene.py`의 관련 사례를 보완하는 방식으로 진행함. 우선 검증 대상은 세션 충돌, 다른 소유자 복구 거부, 제출 여부 불명 시 재전송 방지, 결과 저장 후 정리 순서임.

실환경 검증은 Codex·Claude·agy 각각에서 작은 읽기 전용 미션 하나를 실행하고 비어 있지 않은 결과를 회수함. 같은 세션의 두 번째 미션과 다른 세션의 새 미션으로 Project 재사용/분리를 확인함. dry-run과 프로세스 종료 코드만으로 실환경 통과를 선언하지 않음.

배포 완료 보고에는 소스 변경, 설치본 일치 여부, 실제 사용 경로, 실환경 검증 범위를 명시함. 테스트 성공이 설치나 공개 배포 완료를 뜻하지 않음.
